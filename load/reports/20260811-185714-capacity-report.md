## Root cause (diagnosed after this run)

This run's technical errors are a real payment-api defect, not a test-harness artifact. Two
follow-up checks ruled out the test itself: (1) raising `payment-api`/`payment-sbus` from 1.0 to
2.0 CPU/container did not change the failure pattern — reproduced identically in a targeted
90s/167rps recheck; (2) `p95`/`p99` latencies cluster at exactly ~60000-60011ms across every
failing scenario, k6's own default HTTP request timeout, with the k6 log recording
`"Insufficient VUs, reached 760 active VUs and cannot initialize more"` and repeated
`"Request Failed" error="...request timeout"` — all attributed to a single instance
(`payment-api-2` in the recheck), never `payment-api-1`.

`payment-api-2`'s own container logs explain why: `ResponseCoordinator.complete()`
(`payment-api/src/main/java/com/example/payments/api/coordination/ResponseCoordinator.java:119`)
calls `RedisStatusStore.get()`
(`payment-api/src/main/java/com/example/payments/api/redis/RedisStatusStore.java:73`)
synchronously, from inside the Lettuce PubSub message-listener callback thread. `RedisStatusStore`
holds one unpooled Lettuce connection with no custom command timeout; under sustained concurrent
load that connection's command queue backs up until Lettuce's default 60s command timeout fires:

```
io.lettuce.core.RedisCommandTimeoutException: Command timed out after 1 minute(s)
  at RedisStatusStore.get(RedisStatusStore.java:73)
  at ResponseCoordinator.complete(ResponseCoordinator.java:119)
  at ResponseCoordinator$1.message(ResponseCoordinator.java:78)
```

Because the call blocks the PubSub connection's single Netty event-loop thread, no completion
notification can be delivered on that instance until it clears — and it does not clear on its
own: the same instance's logs show this firing again roughly every 60 seconds
(20:18:11, 20:19:11, 20:20:11, 20:21:12) for the rest of the run. Full evidence:
`load/reports/certified-target/cpucheck.redis-timeout-evidence.txt`.

**Scope:** fixing `RedisStatusStore`'s connection handling is a `payment-api` product change,
outside `load/`'s task boundary (T57's job is to prove and report the gate, not patch the
product under test — same principle T55 followed for its own `RedisStatusStore` finding).
Tracked as follow-up **task_3801253b**, not fixed in this task, per SPEC_DEVIATION below.

CAP-05 (cross-instance duplicate-key coordination) and the recovery scenario's drain behavior
were unaffected by this bug and passed in both profiles — see the per-scenario sections above.

**SPEC_DEVIATION:** none in the criteria T57 covers — the CAP-02 gap is a pre-existing
implementation gap this gate was built to surface, not a deviation of this task's own scope.

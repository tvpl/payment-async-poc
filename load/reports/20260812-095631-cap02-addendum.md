# CAP-02 re-verification addendum — 2026-08-12

Companion note to `20260812-095631-capacity-report.md`, which the gate's own
`generate_report.py` produced automatically from this run and must not be hand-edited.
This addendum records a follow-up investigation into that report's verdict.

## What this run was for

`task_3801253b` (fixed earlier this session, `c722c46`) changed `ResponseCoordinator` to
dispatch Redis PubSub notifications on a virtual thread instead of blocking the shared
event-loop thread. The original T57 report (`20260811-185714-capacity-report.md`) recorded
4.1%–44.4% technical error rate under this exact scenario, caused by that bug. No committed
artifact backed a claim that the fix actually resolved it under real sustained load — this run
closes that gap.

## Result: the technical-error claim is now proven

`certified-target/steady` (167 req/s × 15m, 150,301 requests): **technical error rate =
0.0000%** (`status mix: 200=304 202=22162 422=31 429=127804 technical_errors=0`), vs. 4.1%–44.4%
before the fix. `RedisCommandTimeoutException` — previously recurring every ~60s in the
container logs — did not occur. **CAP-02's `<0.1% technical error` sub-criterion is met and now
has a dated, committed artifact.**

## A different, separate issue: the automated report still says FAIL

`generate_report.py`'s verdict is **FAIL**, because reconciliation reported 2 of 185 sampled
requests (`ce18cc2b-555f-43df-b4da-30e0e63a8de7`, `aeee5820-319f-4a14-bc0b-5e43044cbb8d`) never
reached a terminal state — CAP-02's other sub-criterion, "zero silent loss."

**Investigated and root-caused: this is a false negative in the reconciliation methodology, not
a functional regression.** Both request IDs had already expired out of Redis (payment-api's fast
status store) by the time I checked — but Postgres (`payment_sbus_message`, SBUS's durable
store) shows both reached `COMPLETED` **within ~1 second of being created**:

```
              request_id              |  status   |          created_at           |          updated_at
--------------------------------------+-----------+-------------------------------+-------------------------------
 aeee5820-319f-4a14-bc0b-5e43044cbb8d | COMPLETED | 2026-08-12 09:40:04.152626+00 | 2026-08-12 09:40:05.022264+00
 ce18cc2b-555f-43df-b4da-30e0e63a8de7 | COMPLETED | 2026-08-12 09:40:02.117515+00 | 2026-08-12 09:40:02.317824+00
```

Root cause: `payment-api/src/main/resources/application.yml`'s `payment.status-ttl: 15m` exactly
equals `steady`'s own scenario duration (`manifest.yaml`'s `steady.duration: 15m`).
`reconcile.py` only polls its sampled request IDs **after the whole 15-minute scenario finishes**
(`lib.sh#run_k6_scenario`, `run_gate.sh`/`scenarios/steady.sh` call it as the last step). A
sample logged near the *start* of the run — like both of these (`created_at` ≈ 09:40:0x, seconds
into the run) — has its Redis status entry TTL out at almost exactly the same moment
reconciliation gets around to checking it 15 minutes later. The request itself completed
correctly and fast (sub-second); the test's own check arrived too late to observe it, through no
fault of the request-handling code.

**This is not a new regression** — it is a latent gap in the capacity gate's own reconciliation
design, plausibly present since T57 but masked there by the much larger technical-error failures
dominating that run's narrative. Tracked as a follow-up (`task_...` — see spawned task) rather
than fixed here: fixing it means either polling status shortly after each sample completes
(rather than only once at scenario end) or raising `status-ttl` beyond the longest scenario
duration for gate runs — a design change to the gate's own methodology, not a quick patch.

## Net effect on CAP-02

- **Technical error rate**: ✅ proven met (0.0000%, this run) — was the actual subject of
  `task_3801253b`'s fix and this re-verification.
- **Zero silent loss**: the automated gate still reports FAIL, honestly, because its own
  methodology cannot currently distinguish "genuinely lost" from "TTL'd out before we checked."
  Both apparent losses in this run were confirmed NOT actually lost via a direct Postgres
  cross-check. CAP-02 is not fully certified end-to-end by an unqualified automated PASS; it is
  proven correct by the technical-error metric plus this manual cross-check, with the
  reconciliation methodology itself flagged as needing a fix.

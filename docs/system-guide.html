Como o payment-async-poc funciona

Um workspace de oito fronteiras independentes que provam, de ponta a ponta, um padrão síncrono-sobre-assíncrono: a API HTTP responde rápido quando pode, degrada para 202 quando não pode, e nunca perde uma requisição no caminho. Este guia explica cada camada, por que ela existe, e o que quebra se ela não existir — com um simulador visual para ver o fluxo acontecer.

Mapa do sistema

O fluxo principal é síncrono na entrada, assíncrono por dentro: o cliente faz uma chamada HTTP comum, mas por baixo a requisição atravessa duas passagens pelo Kafka antes de qualquer resposta existir. payment-api nunca fala diretamente com o Core — só payment-sbus fala, e só por evento.

Linha sólida = chamada em runtime · borda tracejada = opcional, infra ou NON_PRODUCTION · Kafka, Redis, PostgreSQL e o Registro são todos provisionados pelo sandbox (AD-003) — nenhuma fronteira cria sua própria infraestrutura compartilhada.

E se...?

202O Core demora demais

payment-api espera no máximo payment.simulation.wait-timeout (3s, poll a cada ≤500ms). Estourou o prazo? Responde 202 com uma statusUrl — o resultado não se perde, só chega depois. O cliente faz GET nessa URL quando quiser.

422O Core recusa

payment-core-mock decide de forma determinística (CORE_DECLINE_PCT/CORE_FAIL_PCT). Uma recusa é uma resposta terminal válida — payment-sbus publica PaymentSimulationFailed e o cliente recebe 422, não um erro de infraestrutura.

DLQMensagem envenenada

Payload ilegível, major de evento desconhecido, ou violação de integridade no banco: tudo isso é poison, não transiente. Vai direto pra payment.simulation.dlq com um motivo sanitizado (sem payload, sem PII) — nunca fica reprocessando pra sempre.

503Redis cai

Idempotência não tem substituto local — RedisStatusStore falha fechado: qualquer erro do Redis vira 503 com Retry-After, nunca um "deixa passar sem checar duplicata".

payment-contracts

PRODUCTION

A fundação compartilhada: o envelope de evento, os modelos de payload, e a ponte para Avro/Apicurio. Nenhuma outra fronteira depende do código-fonte de outra — só de coordenadas Maven publicadas. É essa regra, mais do que qualquer ferramenta, que faz o workspace se comportar como oito repositórios de verdade em vez de um monorepo disfarçado.

JavaAvro Apicurio RegistryGradle Maven publish

Dois artefatos, uma regra

payment-contract-modelEnvelope, payloads, constantes de evento/tópico/header, e as classes Avro geradas como Java puro. Zero dependência de Kafka client, Registry, Redis, banco ou HTTP.
payment-contract-avro-apicurioAvroMapper (POJO ↔ Avro) e AvroSerde — um pool fixo de pares serializer/deserializer não-thread-safe, emprestados por operação e devolvidos em finally, evitando lock global sob virtual threads.

POR QUE ISSO IMPORTA EM PRODUÇÃO

Consumir por project(':contracts') (source dependency) parece mais conveniente em dev, mas mascara justamente o que um repositório independente exige provar: que o artefato publicado — não o source tree local — é o que realmente compila e funciona. Um incidente real do workspace (2026-08-12) aconteceu exatamente ao contrário disso: um diretório de publicação local desatualizado de feature-control fez payment-api compilar silenciosamente contra um jar antigo por dias. O gate de release consome só o artefato publicado — é isso que torna esse tipo de incidente detectável.

O envelope

EventEnvelope<T> carrega: eventId, eventType, eventVersion, occurredAt, requestId, correlationId, causationId, traceId, source, tenantId, payload. Note o que não está aqui: a Idempotency-Key nunca viaja no envelope — ela vive só no Redis de payment-api e na tabela idempotency_record de payment-sbus, escopadas por tenant.

Compatibilidade de schema

Toda mudança passa por checagem FULL_TRANSITIVE local antes de publicar. Uma mudança incompatível cria major/artefato/tópico novos, coexistindo com a versão antiga — nunca um BACKWARD-only silencioso, porque produtor e consumidor não migram atomicamente.

GUARDA DE CAMPO SENSÍVEL

SensitiveFieldGuardUnitTest escaneia reflexivamente toda classe em com.example.payments.common.model e quebra o build se um nome de campo contiver pan, card, cvv, password, secret, token (case-insensitive). É uma política de forma (nome do campo), não um scanner de conteúdo — mascaramento de PAN real e criptografia de campo continuam fora de escopo.

payment-api

PRODUCTION_CANDIDATE

A entrada HTTP síncrona sobre o fluxo assíncrono. Recebe POST /payment-simulations, publica no Kafka, e espera — barato, numa virtual thread — pela resposta correlacionada. Devolve o resultado se ele chegar a tempo; devolve 202 com uma URL de status se não chegar. Nunca fala com o Core diretamente.

Anatomia de uma requisição

  1. Auth — ApiKeyFilter: hash SHA-256 comparado em tempo constante.
  2. Admissão — ConcurrencyLimitFilter: janela deslizante no Redis, orçamento de rota e de tenant num único round-trip Lua.
  3. Tenant — TenantResolver: resolvido da credencial (nunca do header sozinho, ver Tenant & segurança).
  4. Idempotência — Idempotency-Key obrigatória; fingerprint SHA-256 dos campos de negócio; SET NX escopado por tenant.
  5. Publica — PaymentSimulationRequested no Kafka, sob um orçamento de 500ms (max.block.ms, ver BUDG-01 abaixo).
  6. Espera — ResponseCoordinator registra um CompletableFuture, espera até payment.simulation.wait-timeout (3s), em fatias de ≤500ms que reconferem o Redis (cobre uma notificação de pub/sub perdida).
  7. Responde — 200 (aprovado), 422 (recusado), ou 202 com statusUrl se o prazo estourar.

POR QUE O ORÇAMENTO DE PUBLISH É 500ms

PublishBudgetProducerCustomizer deriva delivery.timeout.ms/max.block.ms/request.timeout.ms desse único valor. PublishBudgetGuard falha o boot se esse orçamento não for menor que o wait-timeout — assim um publish travado nunca consome sozinho todo o tempo que o cliente esperaria por uma resposta. Sem esse teto, uma falha de rede no Kafka poderia prender a requisição pelos ~30-60s default do cliente Kafka, em vez de devolver um 503 honesto em meio segundo.

Resiliência

Fail-closed no Redis

Idempotência não tem substituto local. Qualquer RedisException vira 503 — nunca "deixa passar sem checar duplicata".

Fallback via SBUS

SbusStatusGateway tem seu próprio circuit breaker (5 falhas seguidas → 30s aberto) para consultar o estado durável quando o Redis não tem nada.

Degradação dupla de orçamento

Sem Redis, rota e tenant degradam cada um pro seu próprio limite local por instância — nunca para o orçamento cheio, que multiplicaria por instância.

Sem waiters vazados

Uma flag reachedAwait garante que qualquer exceção entre registrar e esperar limpa o waiter — sem isso, uma falha ali vazava a entrada pra sempre.

Versionamento

A rota estável (/payment-simulations) nunca emite X-Api-Version. A rota experimental (/v0/payment-simulations) é liberada por feature flag (via feature-control) e devolve 404 — nunca 401/403 — para quem não tem acesso, escondendo até a existência da rota. Detalhe completo em Versionamento.

Por que isso importa

Idempotency-Key é obrigatório, não opcional: o código (IdempotencyKeyValidation) exige o header desde a AD-009 e rejeita com 400 quando ele falta, exatamente para impedir que uma resubmissão sem chave vire uma identidade nova por acidente. O README do boundary já reflete isso.

payment-sbus

PRODUCTION_CANDIDATE

O coordenador assíncrono durável. Consome pedidos e respostas do Core, persiste estado e outbox na mesma transação, publica retries no instante devido, e mantém DLQ recuperável até o broker confirmar. É o único boundary que fala com o Core — payment-api nunca fala diretamente.

O padrão outbox, na prática

Nunca "gravou no banco mas não publicou" (o problema clássico do dual-write) — o outbox garante que os dois fatos nascem juntos ou nenhum nasce.

Por que groupIds separados (AUD-10): antes, todos compartilhavam um só grupo, e um rebalanceamento disparado por qualquer um revogava as atribuições de partição de todos — mesmo consumindo tópicos completamente diferentes.

Poison vs. transiente

Nem toda falha de decodificação é poison. Uma indisponibilidade do Schema Registry é reclassificada como RegistryUnavailableException (transiente/retryable) — senão, um restart rotineiro do Registry mandaria pagamentos válidos direto pra DLQ. Já um major de evento desconhecido, ou uma violação de integridade no banco (SQLState classe 22/23), é sempre poison — repetir não vai mudar o resultado.

Saúde: readiness vs. liveness

Kafka/Postgres/Registry compõem o readiness (tira da rotação do load balancer). Redis é readiness opcional — sua ausência reporta DEGRADED, não DOWN, porque só alimenta o rate limiter do Core, não a durabilidade. HikariPoolHealthIndicator é liveness, não readiness: exaustão de pool não deveria tirar a instância de rotação do jeito que uma dependência real caída deveria.

CORRIGIDO NESTA SESSÃO — FlywayPoolSizeGuard

micronaut-flyway migra a partir de um listener no bean DataSource, e o DbMigrate do Flyway abre uma segunda conexão física enquanto a primeira ainda está em uso. Com maximum-pool-size: 1, o Flyway travava esperando por si mesmo pelos 30s inteiros do connection-timeout — e o boot falhava com uma mensagem do Hikari que nunca mencionava Flyway. FlywayPoolSizeGuard intercepta a configuração do pool (não o pool em si, então roda estruturalmente antes dele existir) e falha em menos de 10s com uma mensagem que nomeia a causa real. Produção usa pool de 10 — nunca foi um bug ativo, só uma armadilha esperando uma configuração futura errada.

payment-core-mock

NON_PRODUCTION

Um substituto determinístico pro "Core" de pagamento real — caro, lento, ou simplesmente inexistente neste PoC. Fecha o laço assíncrono em dev, sem virar dependência de produção disfarçada de dependência de produção.

MicronautKafka Client Avro

Decisão 100% reproduzível

DecisionEngine deriva tudo de SHA-256(CORE_SEED + requestId) — mesma semente, mesmo requestId, mesma configuração, sempre o mesmo resultado, mesmo em redelivery. Três saídas possíveis: APPROVED, DECLINED, TRANSIENT_FAILURE, distribuídas por CORE_DECLINE_PCT/CORE_FAIL_PCT, com latência simulada configurável (CORE_LATENCY_MIN_MS/_MAX_MS).

POR QUE É NON_PRODUCTION — SEM EXCEÇÃO, SEM PROFILE

A ADR-0001 do boundary rejeita explicitamente "promover via profile": um profile não adiciona SLA, regra financeira, segurança ou operação real. A classificação está no boot, na imagem, no README e no CI — nenhuma variável de ambiente remove o status NON_PRODUCTION. Endpoints de management ficam abertos de propósito (AD-005): é um simulador de desenvolvimento, não um serviço exposto.

Caminho de evolução

O boundary payment-sbus já isola "como alcançamos o Core" atrás de uma interface (CoreGateway/KafkaCoreGateway). Substituir este simulador por um Core real — via outra app Kafka, um cliente HTTP/gRPC síncrono, ou um adapter de nomes de tópico — não toca outbox, persistência ou lógica de idempotência.

FALHA SEGURA, NUNCA FALHA ABERTA

Cache local com TTL curto (5s, com jitter). Numa queda do Redis, um valor conhecido-bom só é servido enquanto mais novo que max-stale (5m); depois disso, a política decide: voltar ao YAML baseline, ou fechar (força "off"). O kill-switch inverte esse viés de propósito — na dúvida, ele fica armado, não desarmado.

Dois apps de exemplo (feature-demo, pilot-app) demonstram cada tipo de flag. Cada um carrega um guarda que lança incondicionalmente sob profile=prod — diferente do padrão por-controller de payment-api, porque não existe configuração de prod válida pra um app de demonstração.

gateway

NON_PRODUCTION · opcional

Um guardrail de borda baseado em Envoy, na frente de payment-api. Existe pra exercitar OIDC/JWT, mTLS, rate limit global e circuit breaking de ponta a ponta — sem tocar código de aplicação. É opcional: o fluxo Edge→Sbus→Core funciona normalmente em localhost:8080 sem ele.

EnvoyKeycloak mTLSKubernetes (Envoy Gateway CRDs)

DEFESA EM PROFUNDIDADE, NÃO A ÚNICA BARREIRA

O Envoy injeta X-Tenant-Id a partir do claim JWT (claim_to_headers), depois de remover qualquer valor forjado pelo cliente. Mas isso é só uma camada extra: TenantResolver em payment-api sempre revalida o header contra o binding da API key — comportamento idêntico com ou sem o gateway na frente. Ver Tenant & segurança.

Outras camadas: allowlist de rotas (default-deny), retry assimétrico (GET idempotente reenvia em 5xx, POST só em falha de conexão — nunca reenvia um POST que pode ter chegado), timeout da rota POST (6s) deliberadamente maior que o wait-timeout do Edge (3s) pra o degrade-pra-202 sempre vir da aplicação, nunca de um 504 do proxy.

sandbox

INFRAESTRUTURA LOCAL

A infraestrutura compartilhada de desenvolvimento — Kafka, Redis, PostgreSQL, Registro Apicurio, e opcionalmente Prometheus/Grafana/Jaeger. Não contém build, source, ou contrato de produto: não representa um deployment de produção.

POR QUE SÓ O SANDBOX PROVISIONA INFRA (AD-003)

Se cada boundary criasse seu próprio Kafka/Redis/Postgres, o estado, os recursos e a operação duplicariam por fronteira. Em vez disso, cada app Compose declara a rede do sandbox (payment-sandbox) como externa e resolve dependências pelo DNS dela. Consequência aceita: apps falham de forma clara se a rede ainda não existir — e o workspace pode evoluir a infra sem tocar nenhum source de aplicação.

Dashboards e alertas de cada app são montados read-only a partir do próprio ops/dashboards/ de cada boundary — nunca copiados — via um manifesto versionado. O sandbox só é dono dos próprios dashboards de infraestrutura.

Tenant & segurança

A regra central (AD-008): o tenant efetivo de uma requisição vem sempre do binding credencial→tenants — nunca de um header sozinho, mesmo com o gateway na frente injetando X-Tenant-Id a partir de um JWT válido. O header é sempre revalidado contra o binding da API key; ele nunca é a prova de identidade por si só.

O INCIDENTE QUE MOTIVOU A AD-008

A revisão arquitetural de 2026-08 achou um vazamento cross-tenant crítico: a chave de idempotência era global (idem:{key}, sem tenant) e a constraint do banco também (UNIQUE(idempotency_key)). Um tenant B reenviando o mesmo Idempotency-Key de um tenant A — com o mesmo payload — recebia o resultado de A (código de autorização, taxas). Com um payload diferente, B recebia um 409 de um tenant que nem era o seu. A correção (AD-008): o tenant nunca vem do corpo, o binding vira a única fonte de verdade, e toda chave — Redis, banco, fingerprint, envelope — passa a ser escopada por tenant. No payment-sbus, a unicidade de idempotência virou (tenant_id, idempotency_key), nunca uma chave global.

Idempotency-Key obrigatória (AD-009)

Toda rota de escrita exige Idempotency-Key ([A-Za-z0-9_-]{1,128}), respondendo 400 se ausente ou fora do padrão. Antes da AD-009, o header era opcional e um valor ausente virava um UUID gerado silenciosamente — o que significava que qualquer retry natural do cliente (num 503 ou num 202 por timeout) virava uma operação nova, deixando toda a proteção de idempotência inerte. Janela efetiva: 24h, acima do TTL de status em cache (15m).

Versionamento

Duas estratégias de versionamento coexistem por design (AD-010): a da API HTTP e a do contrato de evento — cada uma resolvendo um problema diferente.

API HTTP

O path só carrega o major quando ele diverge do major estável implícito atual. /payment-simulations (sem prefixo) é a major estável hoje; /v0/payment-simulations é uma major experimental anterior, liberada por feature flag. Toda rota que não for a major estável implícita emite X-Api-Version na resposta.

Eventos Kafka

eventVersion é major.minor (hoje "1.0"). Mudança aditiva/compatível bumpa o minor; mudança quebra bumpa o major. Todo consumidor chama EnvelopeVersions.assertKnownMajor(...) antes de processar.

MAJOR DESCONHECIDO É POISON — NUNCA SILENCIOSO

Um major não reconhecido lança UnknownEventMajorException, tratado como poison → DLQ direta, com motivo explícito. A alternativa — logar e continuar, ou descartar em silêncio — deixaria um deploy divergente entre produtor e consumidor corromper estado a jusante sem ninguém perceber. Como poison, o evento fica visível na DLQ, pronto pra replay assim que um consumidor que entende aquele major existir.

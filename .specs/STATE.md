### Operational lessons from this session (read before dispatching more batches — this is the "melhor" the user asked for)

1. **The Docker daemon dies under sustained IT load** (no systemd in this container — `dockerd` was started manually, then reaped/OOM'd twice, each time silently killing whichever batch worker was mid-`-PwithIT` gate). Manual restart: `nohup dockerd > /tmp/dockerd.log 2>&1 & disown; sleep 6`. A persistent watchdog Monitor (`while true; do docker info >/dev/null 2>&1 || { nohup dockerd >/tmp/dockerd.log 2>&1 & disown; sleep 8; }; sleep 15; done`) was armed mid-session and auto-healed one death already — **but it does not survive a new window/container**, re-arm it as literally the first action on resume, before dispatching any batch.
2. **`payment-api` gradle runs need `PAYMENT_API_KEY` and `JWT_SIGNATURE_SECRET` exported** (`application.yml` has no default for either — `${PAYMENT_API_KEY}` with no fallback). `export PAYMENT_API_KEY=ci-only-required-value JWT_SIGNATURE_SECRET=ci-only-signing-value-with-at-least-32-bytes` before running `./gradlew test` in a *fresh* shell (each Bash tool call is a new shell — batch workers export this themselves inside their own single long-lived session and never notice; only bit when I had to recover a crashed worker's WIP from a fresh shell and a real test failure looked like it, wasn't). `payment-sbus` needs nothing extra — its ITs self-configure Postgres/Kafka/Redis via Testcontainers properties.
3. **`gradlew ... | tail -N` reports `tail`'s exit code, not gradle's** — a red build can surface as "exit code 0" in a background-task notification. Always use `${PIPESTATUS[0]}` (or `set -o pipefail`) and independently re-check `build/test-results/test/*.xml` (`tests=`/`failures=`/`errors=` counts) rather than trusting a notification's summary line.
4. **A sub-agent's own background-bash-then-auto-resume can look like a premature/incomplete finish.** Twice a batch worker's task-notification arrived with an intermediate status ("started the gate, waiting...") instead of the expected `Batch (...) complete` summary; in one case it then resumed itself on its own background task's completion and finished correctly unattended, in the other Docker's death killed it for good mid-gate and it needed manual pickup. **Verify via `git log --oneline` + `tasks.md` checkboxes before assuming success or failure — never trust the notification text alone.**
5. **Recovery playbook for a worker's uncommitted WIP** (used live for T12, T16 — both left complete-looking code and a failing/unrun gate): (a) read the diff, judge if implementation+test look finished; (b) if a test fails, diagnose root cause *before* touching the test — twice it was environment/harness, not a real bug (T12: hand-rolled JSON parsing of Postgres's `jsonb::text` output doesn't match its `"key": "value"` spacing — reuse the `Json` bean pattern from `RecoverableDeadLetterIT` instead; T16: missing `PAYMENT_API_KEY`/`JWT_SIGNATURE_SECRET` in my recovery shell, see lesson 2); (c) re-run the *whole module's* gate, not just the isolated test; (d) do the Test Adequacy Review inline (evidence table); (e) mark `tasks.md` + `spec.md` Verified, one atomic commit, push.
6. **Batch workers are explicitly authorized to `git push` after each successful commit** (a deliberate, scoped exception to the skill's local-commits-only default, granted this session for this branch only, never force-push) — keep restating this in every batch-dispatch prompt; it's what keeps the repo's `stop-hook-git-check.sh` quiet between turns.
7. **Consider smaller batches going forward** (e.g. ~4 tasks instead of ~6-7) given Docker has died mid-batch twice out of three so far — smaller batches mean less rework per crash. Not yet changed in `tasks.md`'s phase structure; a call for whoever resumes to make, weighed against more dispatch/coordination overhead.
